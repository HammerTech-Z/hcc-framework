## 7. Pollution governance RULES to be promoted (8 rules)

The plan and closeout document these rules verbatim. The rules are abstract; they do not depend on local state.

### Rule R1 — P1 tracked_generated_file policy

`docs/knowledge/vault-health-report-2026-06-12.md` is a `tracked_generated_file`:
- It is a tracked file (committed in HEAD history)
- It is externally regenerated by a vault-health scan process
- It is NOT touched by any HCC gate
- The external regeneration cadence is decoupled from HCC slice execution

Treatment:
- The file is NEVER added to `.gitignore` or `.git/info/exclude` (it remains tracked by design)
- The file is NEVER modified by any HCC slice
- Every audit report MUST capture P1 evidence when present: mtime of the file in the audited worktree, generated timestamp parsed from the file header
- P1 mutation is NOT a stop condition for any push; it is recorded as evidence only
- The audit's `files` field lists the P1 file path; the audit's `gates` field records `p1_tracked_generated_evidence_captured`

### Rule R2 — Stale report policy (post-gate re-verify)

Every audit's "clean" claim is a snapshot:
- A "clean" report is valid only at the time it is issued
- The state machine treats the report as `audited` only if a second status check confirms the snapshot is still valid
- Drift between snapshot and re-verify is recorded in `block: [drift_found]`
- A re-validation run on the same worktree after a "clean" report may surface new drift and transitions to `NEED_PLAN_REPAIR`

### Rule R3 — Worktree reuse pollution policy

A worktree is `POLLUTED` when:
- It has any uncommitted modification on any forbidden file (see R8)
- It has any uncommitted modification on a `tracked_generated_file` (P1)
- It has been replaced by a fresh worktree at the same base commit

Treatment of polluted worktrees:
- Marked as `FROZEN_DO_NOT_USE` in a registry
- No git command is run on a `FROZEN_DO_NOT_USE` worktree (read-only is allowed)
- Future revalidations of the same base commit MUST create a fresh worktree
- To unfreeze, the worktree must be deleted (`git worktree remove`) and a fresh worktree created at the same base

### Rule R4 — FROZEN_DO_NOT_USE policy as a rule

The `FROZEN_DO_NOT_USE` status is a per-worktree flag:
- It is set when a worktree is POLLUTED (R3)
- It prevents any future HCC gate from running on that worktree
- Reading files in a `FROZEN_DO_NOT_USE` worktree is allowed only for diagnosis
- The rule is a STATUS, not a directory move; moving worktree directories is risky and forbidden
- Future revalidations of the same base commit MUST use a fresh worktree, NOT unfreeze the frozen one

### Rule R5 — Main physical worktree risk policy

The main physical worktree (the repo's primary checkout) is:
- Treated as a dirty baseline by default
- NEVER used as merge or revalidation base
- NEVER used as execution base for any HCC slice
- Read-only status inspection is the only permitted operation
- Any drift in the main worktree (modifications outside the protected layer) blocks mainline execution until independently resolved by a separate UI slice

### Rule R6 — Plan-reality mismatch triggers NEED_PLAN_REPAIR

If any gate contradicts the frozen plan:
- Execution STOPS
- State transitions to `NEED_PLAN_REPAIR`
- The plan is repaired to match local reality (or local reality is repaired to match the plan)
- Only after a clean repair does execution resume

The `count` rule: `git rev-list --count <from>..<to>` MUST equal the count documented in the frozen plan. Any mismatch is a hard stop.

The `log --oneline` rule: `git log --oneline <from>..<to>` MUST produce exactly the count of entries documented in the plan. Any mismatch is a hard stop.

The `HEAD == origin` rule: at every audit point, `git rev-parse HEAD` and `git rev-parse origin/hermes-pro-main` must be in the expected relationship (typically `HEAD` is the strict descendant for push slices, or equal for verification slices).

### Rule R7 — Compact agent packet rule

All audit reports are emitted as `HCCCompactAgentPacket`:
- `v: 1` (exact)
- 8 short fields: `v`, `id`, `s`, `base`, `files`, `gates`, `block`, `next`, `ref`
- Serialized size <= 4096 bytes
- 5 forbidden prefixes: `thought`, `reasoning`, `narrative`, `explanation`, `comment`
- 6 next values: `repair_plan_first`, `continue`, `stop`, `blocked`, `retry`, `collect`
- 7 status values: `frozen`, `issued`, `executed`, `audited`, `need_fix`, `repaired`, `promoted`
- No narrative prose, no reasoning, no explanation fields
- The state machine validates packets before accepting them
